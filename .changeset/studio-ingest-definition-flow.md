The Definition tab of an ingest definition with materialized views opens on what they do: a Flow | Pure switch, a list of the views down the left, each with its number of steps, then of the definition's other data sets, each with its number of columns, and the picked one on the right. A view's head shows its name, its primary key, the classification of its data and the data sets it reads, with its own Edit in Cube and Lineage; below, its flow, drawn read-only by Legend Cube's definition flow, which loads the first time it shows. A view Cube can't draw says why and shows its own Pure. A data set shows its key, the views that read it, and its columns, read-only, in View SQL's table: those it declares, then, muted, those its write mode adds. The names a view reads and the views that read a data set link to each other. While the flow shows, the header keeps View SQL and Create MatView; Pure is the whole definition's Pure, under the header as it was. A definition without materialized views is unchanged. Studio still builds no model of an ingest definition: `getIngestDataSets` reads each data set's name, key, write mode and columns from its JSON, for display. The lineage dialog names the view whose lineage it shows. `describeDefinitionFlowRefusal` is exported, for hosts of the flow to say why Cube can't draw a definition.
