The Definition tab of an ingest definition opens on an Overview, with an Overview | Pure switch. On top, the definition's own section: its name, its doc and the settings every data set follows unless it sets its own (owner, read mode, write mode, data set group, compute), the rest one click away. Below, its materialized views and data sets: a list down the left, each view with its number of steps and each data set with its number of columns, and the picked one on the right. A view shows the classification of its data, its own Edit in Cube and Lineage, then its Flow, drawn read-only by Legend Cube's definition flow, which loads the first time it shows (a view Cube can't draw says why and shows its own Pure), or its Metadata: its key, the data sets it reads, how it is written and stored. A data set shows its Schema, its columns read-only in View SQL's table with their descriptions, then, muted, those its write mode adds, or its Metadata: its key and governance, the views that read it, how it is written, stored and read, a setting it takes from the definition saying so. The names a view reads and the views that read a data set link to each other. While the Overview shows, the header keeps View SQL and Create MatView; Pure is the whole definition's Pure, under the header as it was. A definition without views opens on the Overview too, without loading Cube. Everything the tab shows is read from the definition's specification (`IngestDefinitionEditorState.specification`), rebuilt when its content changes; a definition whose content can't be read shows only its Pure, and says so. Once the documentation registry has entries for them, a help icon beside Overview | Pure opens the Legend Studio guide's page on ingest definitions (`dsl-ingest.concept.element.ingest-definition`), and one in Legend Cube's header, while it builds or edits a materialized view, its section on building a view (`dsl-ingest.concept.element.materialized-view`). The lineage dialog names the view whose lineage it shows. `describeDefinitionFlowRefusal` is exported, for hosts of the flow to say why Cube can't draw a definition.

legend-graph: `getIngestWriteModeColumns` gives the columns a write mode of an ingest definition's specification adds, in the order the engine returns them (`LAKE_DIGEST`, `LAKE_IN_ID`, `LAKE_OUT_ID`, then `LAKE_FROM`, `LAKE_THRU`), and `V1_getMilestoningColumnsForWriteMode` gives them in that order too, so an ingest data set's relation type, e.g. in the query builder and Data Cube, lists them in it; `getIngestDatasetWriteMode` gives a data set's write mode, its own else its definition's. `graphManager.getIngestDatasetsReadByRawLambda` gives the ingest data sets a lambda reads, `#I{definition.dataSet}#`, with no engine call. `getRelationColumnTypeLabel` gives a relation column's type with its parameters, e.g. `Varchar(32)`, which the query builder's relation explorer and View SQL's schema now use.
